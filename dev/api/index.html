Emulator interface

AbstractCosmologicalEmulators.AbstractTrainedEmulators — Type
AbstractTrainedEmulators

Common supertype for trained neural-network backends and the normalized GenericEmulator wrapper. Evaluate an explicit emulator with run_emulator; constructing an object does not train a network.

source
AbstractCosmologicalEmulators.GenericEmulator — Type
GenericEmulator(; TrainedEmulator, InMinMax, OutMinMax, Postprocessing)

Wrap a trained backend with feature/output min–max normalization and an explicit postprocessor. InMinMax and OutMinMax have one row per feature/output and two columns containing its minimum and maximum. Postprocessing is called as Postprocessing(input_params, denormalized_output, emulator).

Use (input, output, emulator) -> output for identity postprocessing. Keep normalization ranges consistent with the training artifact; do not re-fit them to an inference batch.

LuxEmulator(; Model, Parameters, States, Description=Dict())

Lux network with explicit trained parameters and inference states. This is the default backend of AbstractCosmologicalEmulators.load_trained_emulator and the supported neural backend for Reactant. See run_emulator for state semantics.

AbstractCosmologicalEmulators.SimpleChainsEmulator — Type
SimpleChainsEmulator(; Architecture, Weights, Description=Dict())

Host-side SimpleChains network and its trained flat weight vector. Input vectors represent one sample; input matrices use features in rows and samples in columns. This backend is not supported by to_reactant.

source
AbstractCosmologicalEmulators.run_emulator — Method
run_emulator(input, emulator)

Evaluate the explicitly supplied trained emulator. Neural backends accept a feature vector or a feature-by-sample matrix. A GenericEmulator normalizes inputs, evaluates its backend, denormalizes outputs, and calls Postprocessing(input, output, emulator). The postprocessor determines the final output shape and must support the desired batching and AD backend.

LuxEmulator uses its stored parameters and states; the state returned by Lux.apply is not written back into the emulator. This is an inference API, not a stateful training step.

source
AbstractCosmologicalEmulators.init_emulator — Method
init_emulator(NN_dict, weights, backend; validate=true, validate_weights=validate)

Construct a trained LuxEmulator or SimpleChainsEmulator from an architecture dictionary and its flat trained weights. The dictionary describes input/output sizes, hidden layers, activations and emulator metadata. This does not apply normalization or postprocessing; use AbstractCosmologicalEmulators.load_trained_emulator for a complete on-disk artifact. Validation is enabled by default.

source
AbstractCosmologicalEmulators.load_trained_emulator — Function
AbstractCosmologicalEmulators.load_trained_emulator(path; backend=LuxEmulator,
    weights_file="weights.npy", inminmax_file="inminmax.npy",
    outminmax_file="outminmax.npy", nn_setup_file="nn_setup.json",
    postprocessing_file="postprocessing.jl", validate=true)

Load an artifact directory into a GenericEmulator. The files contain trained weights, input/output normalization ranges and architecture/metadata. Use the qualified name: this loader is not part of the exported namespace.

An explicitly named built-in postprocessor in nn_setup.json takes precedence; an unknown identifier raises an error. With no named postprocessor, the loader evaluates postprocessing.jl if present, otherwise uses identity. Loading custom postprocessing executes Julia code: load only trusted artifacts. Validation is enabled by default; changing it does not make untrusted code safe.

Normalization, validation and Akima/cubic interpolation

AbstractCosmologicalEmulators.AkimaSpline — Type
AkimaSpline(u, t)

Construct a reusable one-dimensional Akima spline through $(t_i, u_i)$. Evaluate the returned object as spline(t_new). For one-shot evaluation use akima_interpolation; for changing values on fixed grids use AkimaSplinePlan.

Arguments

  • u: Ordinates (function values) $u_i$ at the data nodes.
  • t: Strictly increasing abscissae (knots) $t_i$ associated with u. length(t) must equal size(u, 1). Matrix columns are independent series.

Returns

A callable spline with cached coefficients. With vector ordinates, a scalar query returns a scalar and a query vector returns a vector. For matrix ordinates, use a query vector to obtain a query-by-series matrix.

Details

This routine implements the original Akima piecewise-cubic method (T. Akima, 1970). On each interval $[t_j, t_{j+1}]$, a cubic polynomial is constructed. The method uses a weighted average of slopes to determine the derivative at each node, which effectively dampens oscillations without explicit shape constraints. The resulting spline is $C^1$ continuous (its first derivative is continuous) but generally not $C^2$.

Formulae

The spline on the interval $[t_j, t_{j+1}]$ is a cubic polynomial:

\[S_j(w) = u_j + b_j w + c_j w^{2} + d_j w^{3}, \qquad w = t - t_j\]

The derivative $b_j$ at each node is determined by Akima's weighting of local slopes $m_j=(u_{j}-u_{j-1})/(t_j-t_{j-1})$:

\[b_j = \frac{|m_{j+1}-m_{j}|\,m_{j-1} + |m_{j-1}-m_{j-2}|\,m_{j}} {|m_{j+1}-m_{j}| + |m_{j-1}-m_{j-2}|}\]

The remaining coefficients, $c_j$ and $d_j$, are found by enforcing continuity of the first derivative:

\[c_j = \frac{3m_j - 2b_j - b_{j+1}}{t_{j+1}-t_j}\]

\[d_j = \frac{b_j + b_{j+1} - 2m_j}{(t_{j+1}-t_j)^2}\]

Automatic Differentiation

The implementation is free of mutation on the inputs and uses only element-wise arithmetic, making the returned value differentiable with both ForwardDiff.jl (dual numbers) and Zygote.jl (reverse-mode AD). You can therefore embed akima_interpolation in optimization or machine-learning pipelines and back-propagate through the interpolation seamlessly.

Notes

The implementation is self-contained and has no interpolation-package dependency.

source
AbstractCosmologicalEmulators.AkimaSplinePlan — Type
AkimaSplinePlan(t, t_new)

Prepare the grid-dependent work for repeatedly interpolating changing values u from the fixed knots t onto the fixed query grid t_new.

plan = AkimaSplinePlan(t, t_new)
u_new = plan(u)

Akima coefficients depend nonlinearly on u, so they are recomputed for each call. The plan precomputes the target interval indices and offsets, avoiding repeated searches when t and t_new are fixed.

source
AbstractCosmologicalEmulators.CubicSpline — Type
CubicSpline(u, t)

Prepare a natural cubic spline interpolant for repeated evaluation.

The values u may be a vector or a matrix whose columns are independent data series sharing the strictly increasing knot vector t. The spline coefficients are computed once during construction. Evaluate the prepared spline by calling it on a scalar or vector of query points:

spline = CubicSpline(u, t)
u_new = spline(t_new)

This is equivalent to cubic_spline_interpolation(u, t, t_new) but avoids recomputing the spline coefficients when evaluating the same interpolant at multiple target grids.

source
AbstractCosmologicalEmulators.CubicSplinePlan — Type
CubicSplinePlan(t, t_new)

Prepare a natural-cubic-spline interpolation plan for fixed source knots t and fixed query points t_new, with changing values u:

plan = CubicSplinePlan(t, t_new)
u_new = plan(u)

For fixed knots, the natural-spline second derivatives are a linear function of u. The plan precomputes that linear operator together with all target-grid interval indices and evaluation weights. Calling the plan therefore requires only a matrix-vector or matrix-matrix product and indexed arithmetic.

The second-derivative operator is dense, so plan construction and storage scale quadratically with the number of source knots. Applying a completed plan costs O(n_knots^2 + n_query) for one value vector and O(n_knots^2 * n_series + n_query * n_series) for a matrix of independent series. This representation is intended for moderate, repeatedly reused grids and accelerator/JIT execution.

source
AbstractCosmologicalEmulators.akima_interpolation — Method
akima_interpolation(u::AbstractMatrix, t, t_new)

Akima spline interpolation for multiple data series sharing the same x-coordinates. Uses a simple comprehension-based approach that is compatible with automatic differentiation.

Arguments

  • u::AbstractMatrix: Data values with shape (n_points, n_columns).
  • t: X-coordinates shared by all columns.
  • t_new: Query points.

Returns

Matrix of interpolated values with shape (length(t_new), n_columns).

Example

# Interpolate 11 Jacobian columns at 100 k-points
k_in = range(0.01, 0.3, length=50)
k_out = range(0.01, 0.3, length=100)
jacobian = randn(50, 11)  # 11 parameters

result = akima_interpolation(jacobian, k_in, k_out)  # (100, 11)

B-splines

AbstractCosmologicalEmulators.CubicBSpline — Type
CubicBSpline{X, B, C, E}

A callable cubic B-spline interpolator representing the function values through pre-solved coefficients.

source
AbstractCosmologicalEmulators.CubicBSpline — Method
CubicBSpline(u, x; extrapolation=:clamp)

Construct a not-a-knot cubic B-spline through ordinates u at interpolation sites x. The sites must be a finite, strictly increasing vector with at least four entries. For matrix u, size(u, 1) == length(x) and each column is an independent series.

Calling the result with a scalar query returns a scalar for vector ordinates or a series vector for matrix ordinates. A vector query returns a vector or an nquery × nseries matrix. Extrapolation policies are :clamp, :throw, and :zero.

The spline owns a snapshot of its source sites; changing the original input cannot invalidate cached coefficients or derivatives. Do not mutate stored geometry. Endpoint equality selects the interior derivative in all AD backends.

ForwardDiff, Zygote, and Mooncake support derivatives through ordinates, sites, and query coordinates on plain Julia arrays.

In compiled Reactant evaluation, dynamic extrapolation=:throw is unsupported because XLA cannot lower data-dependent exceptions. Use :clamp or :zero for dynamic device queries.

source

source
AbstractCosmologicalEmulators.CubicBSplinePlan — Method
CubicBSplinePlan(x, xq; extrapolation=:clamp)

Prepare a not-a-knot cubic B-spline plan for fixed source sites x and fixed query points xq, with changing vector or matrix ordinates. Each matrix column is treated as an independent series.

Sites must be finite, strictly increasing, and contain at least four entries. Applying the plan to a vector returns a query vector. Applying it to an nsites × nseries matrix returns an nquery × nseries matrix. Reverse-mode AD supports ordinates, sites, and fixed query coordinates.

Source and query coordinates are independent owned snapshots, even when the same input array is passed twice. Changing the original arrays does not change the plan or its derivatives. Direct mutation of stored geometry is unsupported.

The exported plan(u), bspline_coefficients(plan, u), and bspline_basis(plan) operations compose through plan construction. Raw LU factorization storage is structural and is not a differentiable public input.

Plain Julia stores a band factorization and four-entry query stencil. Preparing the plan with Reactant.to_rarray constructs a dense fixed interpolation operator, limited to 64 MiB, so compiled execution and its Enzyme pullback are matrix multiplication and transpose multiplication.

Dynamic compiled Reactant evaluation cannot use extrapolation=:throw; use :clamp or :zero. A fixed plan may use :throw because xq is validated on the host during plan construction.

AbstractCosmologicalEmulators.set_threads — Method
set_threads(n::Integer)

Use up to n threads in AbstractCosmologicalEmulators. This single setting controls both:

  • FFTW: the thread count of FFT plans created afterwards, for example by prepare_chebyshev_plan. Existing plans keep the setting they were created with.
  • B-spline host solves: the task budget for large dense Float32/Float64 coefficient solves in bspline_coefficients, plan evaluation and their Zygote/Mooncake pullbacks.

Julia's default thread pool is fixed at startup, so the B-spline budget is min(n, Threads.nthreads(:default)). Start Julia with --threads=N or JULIA_NUM_THREADS=N to make workers available. FFTW receives n as given. set_threads(1) requests serial host solves and serial newly created FFT plans. Small batches and vectors stay serial. Other kernels retain their serial paths; public input adapters may first convert containers to dense floating-point arrays.

If set_threads has not been called, large coefficient solves may use the whole default pool and FFTW keeps its existing setting. When you already parallelize over independent chains or tasks, call set_threads(1) to avoid oversubscription. Configure before starting concurrent work.

Analytic background extension

Load all four optional dependencies as described in Analytic cosmology, then obtain the module with Base.get_extension(AbstractCosmologicalEmulators, :BackgroundCosmologyExt). Its functions are not re-exported from AbstractCosmologicalEmulators.jl.

BackgroundCosmologyExt.w0waCDMCosmology — Type
w0waCDMCosmology(; ln10Aₛ=3.0, nₛ=0.96, h=0.67, ωb=0.022, ωc=0.12,
                  ωk=0.0, mν=(0.0, 0.0, 0.0), w0=-1.0, wa=0.0,
                  Neff=3.044, neutrino_prescription=:temperature)

Parameters for analytic expansion, distances and scale-independent growth. Load OrdinaryDiffEqTsit5, Integrals, FastGaussQuadrature and SciMLSensitivity, then obtain this API with bg = Base.get_extension(AbstractCosmologicalEmulators, :BackgroundCosmologyExt).

h = H₀/(100 km s⁻¹ Mpc⁻¹). The fields ωb, ωc, ωk are physical densities Ωb h², Ωc h², Ω_k h², not density fractions. Dark energy follows w(a) = w0 + wa*(1-a); its present density is fixed by Friedmann closure. ln10Aₛ and nₛ are stored parameters, not inputs to the background equations.

mν is a tuple or vector of exactly three individual masses in eV. Masses must be finite and nonnegative; zeros are allowed. A scalar total mass is rejected, no splitting is inferred, and oscillation constraints are not imposed. Shape is checked on construction; numerical validity is checked during evaluation. This does not change trained emulator inputs, which still use total mass Σmν.

Neff must be finite and positive. :temperature scales the three species' temperatures by (Neff/3.044)^(1/4) from Tν/Tγ=0.71611, and scales the reference massless remainder by Neff/3.044. :radiation fixes those temperatures and changes only the massless remainder, requiring Neff ≳ 3.0396. Neither prescription rescales the physical masses or the photon temperature, 2.7255 K.

cosmo = bg.w0waCDMCosmology(mν=(0.0, 0.0086, 0.0502), Neff=3.044)
E = bg.E_z([0.0, 1.0, 3.0], cosmo)

These are host calculations, not a full Boltzmann solver or a Reactant backend. See D_f_z for growth normalization and approximation limits.

Return (D, f) from ONE ODE solve. Each is scalar for scalar redshift, or a vector in the original input order for a redshift vector. Prefer this over separate D_z and f_z calls when both are needed.

CBGrowth() uses a cold+baryon source with smooth neutrinos in the expansion. MatterGrowthApprox() adds the mass-induced neutrino density relative to a massless reference at the same temperature and Neff. Neither computes full scale-dependent massive-neutrino perturbation growth.

Normalization is D(aᵢ)=aᵢ, not D(0)=1. Queries must satisfy 1/139 ≤ a=1/(1+z) ≤ 1.01; invalid queries raise ArgumentError. Ωcb0 excludes neutrinos. Masses and Neff follow w0waCDMCosmology. For small parameter derivatives, tighten tolerances (e.g. reltol=1e-9, abstol=1e-11) and verify convergence; defaults are not an accuracy guarantee.
